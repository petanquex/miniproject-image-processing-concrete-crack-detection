## สรุปและข้อสังเกต

1. **ได้ผลตามเป้า:** precision เพิ่มกว่าเท่าตัว ส่วน recall ลดลงเพียง ~0.08 ทำให้ IoU/Dice ดีขึ้นชัดเจน
2. **สิ่งที่เปลี่ยนแล้วได้ผลที่สุด** คือ C ที่สูงขึ้นคู่กับ closing kernel ที่เล็กลง ทั้งสองอย่างช่วยลดพิกเซลพื้นหลังที่หลุดเป็น crack
3. **Trade-off:** ภาพที่รอยร้าวจางหรือ contrast ต่ำ (เช่น 023, 084) ถูกกรองทิ้งมากขึ้น
   ทำให้ precision สูงแต่ recall ตกหนัก
4. **Overfit เล็กน้อย:** บน 25 ภาพที่ใช้จูนได้ Dice 0.527 แต่ทั้ง 118 ภาพได้ 0.487
5. **ค่าที่ดีที่สุดชนขอบช่วงค้นหา:** `C = 15` คือค่าสูงสุดที่ลอง ส่วน `close_ksize = 3`, `open_ksize = 3`
   และ `min_area = 50` คือค่าต่ำสุดที่ลอง ถ้าขยายช่วงออกไปอาจได้ผลดีขึ้นอีก

## 2026-09-20 — รอบ 2: ขยาย grid + แยก train/test

### สิ่งที่แก้ก่อนเริ่ม

วัดความเร็วก่อนแล้วพบว่า 1 combination ใช้เวลาแค่ **0.54 วินาที** บนภาพทั้ง 118 ภาพ
(pre-process ครั้งเดียวแล้วใช้ซ้ำ) แปลว่าข้อจำกัดเรื่องเวลาที่ทำให้รอบแรกต้องจูนบน
subset 25 ภาพนั้นไม่มีอยู่จริง จึงปรับ `src/tune.py` สองเรื่อง:

1. **ขยาย `GRID` ทุกด้านที่ชนขอบในรอบแรก** — รวม 3600 combinations

   | Parameter | รอบ 1 | รอบ 2 |
   |---|---|---|
   | `block_size` | 25, 35, 51, 75 | 15, 25, 35, 51, 75 |
   | `C` | 5, 10, 15 | 10, 12, 15, 18, 21, 25 |
   | `close_ksize` | 3, 5, 7 | **1**, 3, 5 |
   | `open_ksize` | 3, 5 | **1**, 3 |
   | `min_area` | 50, 120, 250 | 10, 20, 35, 50, 80 |
   | `min_aspect` | 2.0, 3.0, 4.0 | **1.5**, 2.0, 3.0, 4.0 |

   `ksize = 1` คือ kernel ขนาด 1x1 ซึ่งไม่เปลี่ยนภาพเลย = "ข้าม step นี้"
   ใส่ไว้เพื่อให้ grid ตอบได้ว่า morphology จำเป็นจริงไหม

2. **เพิ่ม `--holdout`** — แบ่ง train/test แบบ stride (หยิบทุกภาพที่ N) ไม่ใช่ตัดครึ่งหน้า-หลัง
   เพื่อให้สองฝั่งกระจายทั้ง dataset เท่าๆ กัน ค้นหาบน train 59 ภาพ
   แล้ววัดผลบน test 59 ภาพที่ไม่เคยถูกใช้จูน

### ปัญหาที่เจอ: argmax ของ train เชื่อไม่ได้

grid แรก 3600 combinations ให้ผู้ชนะบน train Dice 0.5139 / held-out 0.5122 ดูดี
แต่ค่าที่ชนะยังชนขอบอยู่สองตัว (`min_area = 80` คือค่าสูงสุด, `min_aspect = 1.5` คือค่าต่ำสุด)
จึงยิง grid เสริมเฉพาะจุดนั้นอีก 384 combinations (`min_area` ถึง 250, `min_aspect` ถึง 1.0)

ผลคือค่าที่ **train ดีขึ้น แต่ held-out แย่ลง**:

| params | train Dice | held-out Dice |
|---|---|---|
| `51, 15, 3, 1, area 180, aspect 2.0` | **0.5257** | 0.4884 |
| `35, 18, 1, 1, area 80, aspect 1.5` | 0.5139 | 0.5122 |

นี่คือ overfitting ของขั้นตอน **การเลือกค่า** เอง: เมื่อลองเกือบ 4000 combinations
ตัวที่ได้คะแนน train สูงสุดมักเป็นตัวที่ "ฟลุก" กับภาพไม่กี่ภาพ ไม่ใช่ตัวที่ดีจริง

### วิธีแก้: เลือกแบบ 2 ขั้น ด้วยข้อมูล train ล้วน (`src/select_params.py`)

- **ขั้น 1** คัด 200-300 อันดับแรกตาม mean Dice บน train
- **ขั้น 2** แบ่ง train 59 ภาพเป็น 5 folds คำนวณ Dice ของแต่ละ fold
  แล้วให้คะแนน `mean - std` คือเลือกตัวที่ทั้ง**ดี**และ**นิ่ง** ไม่ใช่ตัวที่พีคเฉพาะบางภาพ
- **test 59 ภาพถูกแตะครั้งเดียว** ตอนรายงานผลตอนท้าย

ผลคือช่องว่าง train/test หายไปเกือบหมด (รอบ 1 ห่าง 0.040, รอบ 2 ห่าง 0.001)

### ผลข้างเคียงที่สำคัญ: grid บอกให้ปิด step 3 และ 4

ค่าที่ชนะแบบไม่บังคับอะไรเลยคือ `close_ksize = 1, open_ksize = 1, min_aspect = 1.0`
ซึ่งแปลว่า **morphology ทั้งก้อนและส่วน aspect ของ shape filter ถูกปิดทิ้ง** เหลือแค่ area filter
เหตุผลคือ `min_area` ทำหน้าที่กำจัด noise ซ้ำกับ opening อยู่แล้ว และรอยร้าวใน CrackForest บางมาก
opening กัดเส้นขาดมากกว่าช่วย

จึงวัดแบบบังคับเปิดแต่ละ step ด้วย protocol เดียวกัน เพื่อดูว่าแต่ละขั้นตอน "ราคา" เท่าไร:

| Variant | บังคับอะไร | Held-out Dice | ทั้ง 118 ภาพ | params |
|---|---|---|---|---|
| A | ไม่บังคับ | **0.5213** | **0.5205** | `35, 15, 1, 1, 120, 1.0` |
| B | morphology เปิด | 0.5003 | 0.4888 | `25, 12, 3, 3, 80, 1.5` |
| C | aspect filter เปิด | 0.5142 | 0.5090 | `25, 12, 1, 1, 80, 2.0` |
| D | เปิดครบ 4 step | 0.5068 | 0.4991 | `51, 15, 3, 3, 80, 3.0` |

**ตัดสินใจเลือก D** เพื่อรักษาโครงสร้าง 4 ขั้นตอนของโปรเจกต์และการแบ่งงานในทีมไว้
ต้นทุนคือ Dice ต่ำกว่า A อยู่ **0.0145** บน held-out ซึ่งถือว่าคุ้ม และตาราง A-D นี้
เอาไปใช้เป็น ablation study ในรายงานได้โดยตรง

### Reproduce

```powershell
# 1) grid search หลัก (3600 combinations, ~16 นาที) + grid เสริมที่ขอบ

# 2) เลือกค่าสุดท้ายแบบ 2 ขั้น (variant full = เปิดครบ 4 step) แล้วเขียน tuned_params.json

```

### 1. Confusion Matrix (`src/evaluate.py`)

เดิม `pixel_metrics()` นับแค่ TP / FP / FN แล้วข้าม TN ไปเลย และไม่เคยแสดงตัวเมทริกซ์ออกมา
มีแต่ค่า metric ปลายทาง ตอนนี้เพิ่ม:

| ฟังก์ชันใหม่ | ทำอะไร |
|---|---|
| `confusion_counts()` | นับ TP / FP / FN / **TN** ของภาพเดียว |
| `metrics_from_counts()` | แปลง confusion matrix เป็น metric (เพิ่ม specificity, accuracy) |
| `total_confusion()` | รวม confusion matrix ของทุกภาพเป็นตัวเดียว |
| `micro_metrics()` | metric แบบ micro: รวมพิกเซลทั้ง dataset แล้วค่อยคำนวณครั้งเดียว |
| `format_confusion()` | พิมพ์เป็นตาราง |

`pixel_metrics()` กับ `average_metrics()` ยังคืนค่าเหมือนเดิมทุกหลัก (ตรวจแล้ว macro Dice = 0.4991 เท่าเดิม)

รวมพิกเซลทั้งหมดก่อนแล้วคำนวณทีเดียว (ภาพที่รอยร้าวยาวมีน้ำหนักมากกว่า) การรายงานทั้งคู่
แสดงว่าคะแนนที่ได้มาจากภาพง่ายไม่กี่ภาพหรือมาจากทั้ง dataset จริง

### 2. Otsu baseline

`tune.py` เดิมค้นหาเฉพาะ adaptive ถ้าเอา params ที่จูนมาเพื่อ adaptive ไปครอบ Otsu ก็ไม่แฟร์
จึงเพิ่ม `--method {adaptive,otsu}` และ `GRID_OTSU` แยกต่างหาก — Otsu เป็น global threshold
ไม่มี window size และไม่มี offset คอลัมน์ `block_size` กับ `C` จึงตั้งเป็น 0 (ไม่ถูกใช้)
และค้นหาเฉพาะพารามิเตอร์ของ morphology กับ shape filter

จูน 3 รอบเพราะค่าที่ชนะชนขอบ grid สองครั้ง:

| รอบ | combinations | ผลที่ได้ | ปัญหา |
|---|---|---|---|
| a | 180 | held-out Dice 0.1311 | `min_area = 120` ชนขอบสูงสุด |
| b | 324 | held-out Dice 0.2791 | `open_ksize = 5` ชนขอบสูงสุด |
| c | 90 | held-out Dice 0.2791 | `open_ksize = 5` ชนะ 7/9/11/15 = เป็นค่าภายในแล้ว ปิดขอบครบ |

สังเกตว่า Otsu ต้องการ `open_ksize = 5` (adaptive ใช้ 3) และ `min_area` ใหญ่กว่ามาก
เพราะ global threshold ทำให้เกิด blob ขนาดใหญ่เต็มภาพ ต้องใช้ opening แรงๆ กวาดทิ้ง

**Adaptive ชนะประมาณ 2 เท่าตัว** เทียบแบบเปิดครบ 4 step เหมือนกัน (0.5068 vs 0.2262)

รายภาพ: **adaptive ชนะ 116 จาก 118 ภาพ** Otsu ชนะแค่ 2 ภาพคือ **023 กับ 104**

adaptive กรองรอยร้าวทิ้งเกือบหมด แต่ global threshold กลับจับได้)

- Dice < 0.2: adaptive 9 ภาพ / Otsu 41 ภาพ

เทียบกับ adaptive: FP เพิ่มจาก 157,115 เป็น **394,732 (2.5 เท่า)** ขณะที่ TP ลดลง
คือ Otsu **ทายว่าเป็นรอยร้าวมากขึ้นแต่ถูกน้อยลง** = over-segmentation ตามที่คาด

### 4. อธิบายผล (ใช้ในรายงานได้)

Otsu หาค่า threshold **ค่าเดียวสำหรับทั้งภาพ** จาก histogram ซึ่งใช้ได้ดีเมื่อแสงสม่ำเสมอ
และภาพมี 2 กลุ่มความสว่างชัดเจน แต่ภาพถนนใน CrackForest มีทั้งเงา คราบ และความสว่าง
ไม่เท่ากันทั่วภาพ ทำให้ threshold เดียวไปตัดเอาบริเวณที่มืดกว่าค่าเฉลี่ย (เงา/คราบ)
มาเป็นรอยร้าวด้วย ส่วน adaptive thresholding เทียบแต่ละพิกเซลกับ**ค่าเฉลี่ยของเพื่อนบ้าน
ในหน้าต่าง 51x51** จึงไม่สนใจว่าโดยรวมภาพนั้นสว่างหรือมืด

นี่คือเหตุผลเชิงตัวเลขที่ใช้ตอบโจทย์ข้อ 5 ได้ว่าทำไมถึงเลือก adaptive เป็นวิธีหลัก

**หมายเหตุเทียบกับ Dorafshan et al. (2016)** ซึ่งใช้ Otsu แล้วได้ผลดี: เปเปอร์นั้นทำกับภาพ
พื้นผิวคอนกรีตระยะใกล้ในสภาพแสงที่ควบคุมได้ ส่วน CrackForest เป็นภาพผิวถนนในเมืองที่มี
texture และแสงไม่สม่ำเสมอ ผลที่ต่างกันจึงไม่ได้ขัดกับเปเปอร์ แต่สะท้อนว่า**เงื่อนไขการถ่ายภาพ
เป็นตัวกำหนดว่า global threshold ใช้ได้หรือไม่** ซึ่งเป็นข้อสรุปที่มีน้ำหนักกว่าการบอกว่าวิธีไหนดีกว่าเฉยๆ

## 2026-09-20 (ต่อ) — Pre-processing, Edge-based baselines, Failure cases

### 1. จูนและ ablate step 1 (pre-processing) — `src/tune_preprocess.py`

**ที่มา:** `tune.py` ทำ pre-process ครั้งเดียวนอกลูปแล้วใช้ซ้ำทุก combination ซึ่งเป็นเหตุผลที่มันเร็ว
แต่ก็แปลว่า `blur_ksize` / `clip_limit` / `tile` **ไม่เคยอยู่ในการค้นหาเลยตั้งแต่ต้นโปรเจกต์**
ค่าที่ใช้มาตลอดคือ default วันแรก และไม่เคยมีตัวเลขยืนยัน

เขียนสคริปต์แยกที่ตรึง step 2-4 ไว้ที่ค่าที่ ship แล้วกวาดเฉพาะ pre-processing (65 combinations
หลังตัดตัวซ้ำ — เมื่อปิด CLAHE ค่า tile ไม่มีผล) ใช้ protocol เดียวกับ `select_params.py`

เพิ่มความสามารถให้ปิดแต่ละขั้นได้ใน `preprocessing.py`: `blur_ksize <= 1` = ไม่เบลอ,
`clip_limit <= 0` = ไม่ทำ CLAHE (ระวัง: ถ้าส่ง 0 เข้า `cv2.createCLAHE` ตรงๆ มันแปลว่า
**ปิดการ clip** ไม่ใช่ปิด CLAHE — คนละความหมาย)

**Ablation ของ step 1:**

| Blur | CLAHE | Dice ดีที่สุด | ค่าที่ดีที่สุด |
|---|---|---|---|
| เปิด | เปิด | **0.4929** | blur 7, CLAHE 2.0/4 |
| ปิด | เปิด | 0.4197 | no blur, CLAHE 1.0/4 |
| ปิด | ปิด | 0.2699 | — |
| เปิด | ปิด | 0.2306 | blur 3 |

อ่านตารางนี้ได้ 2 อย่าง:

1. **CLAHE คือหัวใจของ step 1** ถ้าเอาออก Dice ตกจาก 0.49 เหลือ 0.23 คือหายไปกว่าครึ่ง
   เพราะ adaptive threshold ต้องการ local contrast ที่ชัดพอจะแยกรอยร้าวจากผิวถนน
2. **Blur อย่างเดียวทำให้แย่ลง** (0.2306) แย่กว่าไม่ทำอะไรเลย (0.2699) ด้วยซ้ำ
   เพราะรอยร้าวบางมาก การเบลอไปกลบมันทิ้งโดยไม่ได้อะไรคืน — blur จะคุ้มก็ต่อเมื่อมี CLAHE
   ดึง contrast กลับมาให้ นี่คือ **interaction** ที่ไม่เห็นถ้าทดสอบทีละตัว

**ค่าที่ชนะคือ `blur 5, CLAHE 2.0, tile 8` ซึ่งตรงกับ default เดิมพอดี** — ไม่ต้องเปลี่ยนอะไร
แต่ตอนนี้มันเป็นค่าที่**พิสูจน์แล้ว** ไม่ใช่ค่าที่เดาไว้

**เช็ค bias:** ค่า step 2-4 ที่ใช้ตรึงถูกจูนมาบน pre-processing ชุดเดิม จึงเข้าข้างค่าเดิมอยู่กลายๆ
เพิ่ม `--joint` ที่ re-optimize step 2-4 ใหม่ให้ candidate แต่ละตัวจาก shortlist 200 อันดับแรก:

| Pre-processing | steps 2-4 ที่ re-optimize แล้ว | Held-out Dice |
|---|---|---|
| blur 5, CLAHE 2.0/8 (ปัจจุบัน) | 51, 15, 3, 3, 80, 3.0 | 0.5068 |
| blur 5, CLAHE 2.0/4 | 51, 21, 5, 3, 50, 3.0 | 0.5115 |
| blur 7, CLAHE 2.0/4 | 35, 15, 5, 3, 50, 3.0 | 0.5102 |
| blur 7, CLAHE 2.0/8 | 35, 15, 5, 3, 50, 3.0 | 0.5080 |
| blur 9, CLAHE 2.0/8 | 25, 10, 3, 3, 80, 2.0 | 0.5109 |

ทั้ง 5 ตัวห่างกันไม่เกิน 0.005 → **pre-processing ไม่ใช่ปุ่มที่ไว** ตราบใดที่ยังเปิด CLAHE ไว้
ตัวเลข 0.5115 ที่ดูสูงกว่านั้นเลือกจาก held-out ซึ่งเป็นการแอบดูข้อสอบ จึงไม่เอามาใช้
ยึดตาม protocol เดิมคือเลือกจาก train → ได้ค่า default เดิม ไม่เปลี่ยนค่าที่ ship

### 2. Edge-based baselines (Canny / Sobel)

โจทย์ข้อ 4 ต้องการให้ literature review อธิบายเหตุผลที่เลือก threshold-based แทน edge-based
การมีตัวเลขของตัวเองมายันหนักแน่นกว่าการอ้างเปเปอร์อย่างเดียว

เพิ่ม `segment_canny()` และ `segment_sobel()` ใน `segmentation.py` และ `--method canny|sobel`
ทั่วทั้ง pipeline โดยใช้ parameter schema เดียวกัน (`canny_lo` / `canny_hi` เพิ่มเข้า `KEYS`
ส่วน method อื่นตั้งเป็น 0)

**ข้อควรรู้เรื่อง Canny:** มันหา**ขอบ**ของรอยร้าว ไม่ใช่ตัวรอยร้าว รอยร้าวหนึ่งเส้นจึงออกมาเป็น
เส้นคู่ขนานสองเส้นที่มีช่องว่างตรงกลาง ต้องพึ่ง closing มาเชื่อมกลับ แต่ถ้า closing แรงไปก็พัง:
บนผิวถนนที่มี texture Canny ที่ threshold ต่ำจุดติดประมาณ **27% ของพิกเซลทั้งภาพ** แล้ว
closing kernel 7 จะหลอมทุกอย่างเป็นก้อนเดียวกินพื้นที่ 75% ของภาพ ซึ่ง shape filter ตัดทิ้งทั้งก้อน
ได้ Dice 0.0000 (รอบแรกที่ผมตั้ง grid ผิดก็เจอแบบนี้ทั้งกระดาน)

ช่วงที่ใช้ได้จริงคือ **edge map ที่เบาบาง + kernel เล็ก** จึงจูน 2 รอบ (864 + 432 combinations)
จนค่าที่ชนะไม่ชนขอบ

> หมายเหตุ: ค่าที่ชนะออกมาเป็น `canny_lo = 200, canny_hi = 150` ซึ่งดูสลับกัน — ตรวจแล้วว่า
> `cv2.Canny(g, 200, 150)` ให้ผลเท่ากับ `cv2.Canny(g, 150, 200)` ทุกพิกเซล OpenCV ใช้ค่าน้อย
> เป็น hysteresis low เอง ลำดับใน grid จึงไม่มีผล

**Sobel** ใช้ gradient magnitude แล้ว threshold (`canny_lo = 0` หมายถึงใช้ Otsu บน magnitude)
จูน 432 combinations

### 3. ผลเปรียบเทียบ 4 วิธี (protocol เดียวกันทั้งหมด เปิดครบ 4 step)

| Method | Held-out Dice | 118 ภาพ macro | 118 ภาพ micro | Dice >= 0.5 | Dice < 0.2 | ชนะขาด (จาก 118) |
|---|---|---|---|---|---|---|
| **Adaptive** | **0.5068** | **0.4991** | **0.4708** | **68** | **9** | **108** |
| Sobel | 0.3180 | 0.2956 | 0.2768 | 12 | 38 | 7 |
| Canny | 0.2278 | 0.2127 | 0.1959 | 7 | 64 | 3 |
| Otsu | 0.2262 | 0.2433 | 0.2612 | 8 | 41 | 1 |

**Adaptive ชนะขาด 108 จาก 118 ภาพ** และดีกว่าอันดับสอง (Sobel) ประมาณ 1.6 เท่า

**False positive เทียบกัน** (จาก confusion matrix): adaptive 157,115 / Sobel 334,623 /
Canny 476,609 / Otsu 394,732 พิกเซล — ทุก baseline ทายเกินหมด

**อธิบาย:** Canny กับ Sobel ตอบสนองต่อ**การเปลี่ยนความสว่างอย่างฉับพลัน** ซึ่งบนผิวถนน
มีเต็มไปหมดจาก texture ของยางมะตอย ขอบคราบ และเงา — ทั้งหมดนี้มี gradient แรงพอๆ กับ
ขอบรอยร้าว ขณะที่ adaptive thresholding ถามคำถามที่ตรงกว่าคือ "พิกเซลนี้**มืดกว่า**เพื่อนบ้าน
หรือเปล่า" ซึ่งรอยร้าวตอบว่าใช่ แต่ texture ที่สว่าง-มืดสลับกันตอบว่าไม่

สังเกตว่า Sobel ชนะ Canny — เพราะ Canny มีขั้น non-maximum suppression + hysteresis
ที่ทำให้ได้เส้นขอบบาง 1 พิกเซล ซึ่งยิ่งทำให้ปัญหา "เส้นคู่ขนานรอบรอยร้าว" ชัดขึ้น
ส่วน Sobel ให้แถบ gradient ที่หนากว่า จึงบังเอิญทับตัวรอยร้าวได้มากกว่า

## 2026-09-20 (ต่อ) — รอบ 3: แก้เกณฑ์รูปทรงใน step 4

ทำตามข้อเสนอในหัวข้อ 5 ของบันทึกก่อนหน้า

### 1. สิ่งที่แก้ใน `src/shape_filter.py`

**ปัญหาที่ 1 — วัดความเรียวผิดวิธี.** เดิมใช้ aspect ratio ของ `cv2.minAreaRect`
ซึ่งตั้งอยู่บนสมมติฐานว่ารอยร้าวเป็นเส้นตรง รอยร้าวที่โค้งหรือแตกแขนงมีกรอบครอบเกือบเป็น
จัตุรัสจึงถูกตัดทิ้งทั้งก้อน

เปลี่ยนไปใช้ **circularity** = `4*pi*area / perimeter^2` ซึ่งได้ค่าใกล้ 1.0 สำหรับวงกลม
และใกล้ 0 สำหรับอะไรก็ตามที่เรียว **ไม่ว่าจะโค้งแค่ไหน** — เป็นค่าที่ไม่ขึ้นกับรูปร่างการโค้งงอ

**ปัญหาที่ 2 — วัดพื้นที่ผิดวิธี.** เดิมใช้ `cv2.contourArea()` ซึ่งคือพื้นที่ของรูปหลายเหลี่ยม
ที่ contour ล้อม ไม่ใช่จำนวนพิกเซลจริง เปลี่ยนไปใช้ `connectedComponentsWithStats`
ที่ให้จำนวนพิกเซลจริง (ผลข้างเคียง: ความหมายของ `min_area` เปลี่ยน ช่วงที่เหมาะสมจึงขยับขึ้น)

เก็บทั้งสองเกณฑ์ไว้และปิดได้ทั้งคู่ เพื่อให้ grid เป็นคนตัดสินเองว่าอันไหนดีกว่า:
`min_aspect <= 1.0` ปิดเกณฑ์เดิม, `max_circ >= 1.0` ปิดเกณฑ์ใหม่

ของใหม่**เร็วกว่า**ของเดิมเล็กน้อยด้วย (1.2 vs 1.5 ms/ภาพ) เพราะกรองด้วยพื้นที่ก่อน
แล้วค่อยคำนวณรูปทรงเฉพาะก้อนที่รอด

### 2. จูนรอบ 3 (4,800 combinations)

ใส่ `max_circ` เข้า grid คู่กับ `min_aspect` เพื่อเทียบตัวต่อตัวในการค้นหาเดียวกัน

**เกณฑ์รูปทรงแบบไหนดีที่สุด (Dice สูงสุดบน train):**

| เกณฑ์ step 4 | n | Dice |
|---|---|---|
| **circularity อย่างเดียว** | 1920 | **0.5243** |
| ไม่กรองรูปทรงเลย (เหลือแค่ area) | 480 | 0.5201 |
| ใช้ทั้งสองเกณฑ์ | 1920 | 0.5030 |
| aspect ratio อย่างเดียว (แบบเดิม) | 480 | 0.4997 |

**นี่คือผลที่สำคัญที่สุดของรอบนี้:** เกณฑ์เดิม **แย่กว่าการไม่กรองรูปทรงเลย** (0.4997 < 0.5201)
แปลว่าตลอดมา step 4 ส่วนที่เป็น shape analysis ทำให้ผลแย่ลง ไม่ใช่ดีขึ้น
ส่วนเกณฑ์ใหม่ดีกว่าการไม่กรอง (0.5243 > 0.5201) — เพิ่งจะมีเหตุผลเชิงตัวเลข
ให้ขั้นตอนนี้มีอยู่ในไปป์ไลน์เป็นครั้งแรก

อธิบายย้อนหลังได้ด้วยว่าทำไม `min_aspect` ถึงวิ่งชนค่าต่ำสุดของ grid ทุกรอบที่ผ่านมา
และทำไม variant "ไม่บังคับ" ถึงชนะตลอด — grid พยายามจะปิดเกณฑ์ที่เสียอยู่ตลอดเวลา

### 3. Head-to-head ด้วย protocol เต็ม (เปิดครบ 4 step)

| **full_circ** (เกณฑ์ใหม่) | **0.5105** | **0.5024** | 35, 15, 3, 3, area 120, circ 0.4 |

เพิ่ม variant `full_aspect` / `full_circ` เข้า `select_params.py` เพื่อบังคับให้ step 4
ใช้เกณฑ์ใดเกณฑ์หนึ่งขณะที่ step อื่นเปิดครบเหมือนกัน

### 5. สิ่งที่รูปใหม่บอก: failure case ที่เหลือบางส่วนเป็นปัญหาของ ground truth

ดู `outputs/figures/failure_cases.png` ที่สร้างใหม่:

- **021** — ตอนนี้ลากตามรอยร้าวได้ดี (recall 0.756) แต่ precision แค่ 0.239 เพราะมันไป
  จับ**รอยแตกลายงาบนเส้นจราจรสีขาว**ด้วย ซึ่งเป็นรอยแตกจริงๆ แต่ ground truth ของ
  CrackForest ไม่ได้นับไว้ → คะแนนต่ำเพราะนิยามของเฉลย ไม่ใช่เพราะตรวจผิด
- **084** — ground truth วาดรอยร้าวไว้**หนากว่ารอยจริงมาก** (เป็นแถบทึบ) ขณะที่ผลทำนาย
  เป็นเส้นบางตามรอยจริง ทำให้ recall ถูกจำกัดที่ 0.383 ทั้งที่ P สูงถึง 0.711
- **042** — อันนี้ fail จริง รอยร้าวจางมากจนแทบไม่มี contrast

ประเด็นนี้ใส่รายงานได้ดี: **pixel-level metric ลงโทษการตรวจเจอสิ่งที่คนวาดเฉลยไม่ได้วาด**
และความหนาของเส้นในเฉลยมีผลต่อ recall โดยตรง

### 6. Baseline ทั้งสามได้ใช้เกณฑ์ใหม่ด้วย (เพื่อความเป็นธรรม)

(ตรึง segmentation + morphology ไว้ที่ค่าเดิม กวาดเฉพาะ `min_area` / `min_aspect` / `max_circ`)

ผลคือ **ทั้งสามตัวเลือก `max_circ = 1.0` คือปิดเกณฑ์ใหม่ทิ้ง** — สมเหตุสมผล เพราะ mask
ของ baseline เป็นก้อน noise ไม่ใช่โครงสร้างเรียว ตัวกรองความเรียวจึงแยกสัญญาณออกจาก
noise ไม่ได้ เกณฑ์ใหม่ช่วยเฉพาะกับ adaptive ที่ mask เป็นเส้นอยู่แล้ว
